# Decision log

Format: date, decision, reason, discarded alternatives.

## 2026-10-20: Release 1.0.0 with the mod API frozen at 1.0 (user decision)

- **Decision (user's):** release version **1.0.0** dated 2026-10-20 (`Cargo.toml`, `CHANGELOG.md`). The mod API 0.43 is frozen as **1.0** with no change in format or function (`VERSAO_API = "1.0"` in `engine/src/scripts.rs`; line `1.0` in the history of `docs/api-mods.md`). From 1.0 on, the API follows semantic versioning: 1.x versions only add compatible things (optional keys, files, functions, hooks); removing or changing the meaning of something requires 2.0, announced in an earlier 1.x. The only pending removal (the old copies of the common tables, 0.20) moves to 2.0.
- **Reason:** players and modders need a stable reference for the first public version; a 1.0 number says that mods written now keep working in 1.x.
- **Discarded:** keeping the API at 0.x after the release (gives no compatibility promise); numbering the API together with the port (they change at different paces: a port fix does not change the API).
- **Compatibility:** a script that compares `API_VERSAO` with `"0.43"` as text needs to accept `"1.0"`; the example mods only print the value.

## 2026-10-19: Windows 3.1 frame on by default in 1.0; the window controls always work (user decision)

- **Decision (user's):** "Yes, the Windows 3.1 frame comes on by default in 1.0". `data/video.json` → `moldura_windows31` becomes `true` (with `substituir_moldura_do_sistema` = `true`, already the default); a missing key also counts as `true` (`ConfigVideo`), and the launcher's "Moldura Win 3.1" checkbox comes checked (unchecked, it writes `--sem-moldura`). This revokes the evaluation in "Windows 3.1 title bar optional, off by default" and the item "Evaluation of leaving the frame on by default" of "Windows 3.1 frame in place of the system one", below.
- **Automation unchanged:** non-interactive runs (`Opcoes::automacao`: `--exportar-telas`, `--exportar-tela-jogo`, `--ticks`, `--avancar-ms`, `--salvar`, `--sair-apos-ms`, `--capturar-janela`, `--exportar-som`, the same ones that already ignored `launcher.json`) stay **without** the frame unless `--moldura` is given explicitly: the opening exports remain 640 × 442, the window capture 640 × 461 (client area and menu bar), and the hash tests, the vectors and the comparison tools (`tools/comparar_*.py`) produce the same as before. `--exportar-tela-jogo` is only the client area, with or without the frame.
- **Window controls always active (port extension, user request):** with the Windows 3.1 bar in place of the system frame, it is the executable's real frame, so minimize, maximize/restore, the box (the system menu) and double-clicking it also work with a Windows dialog open (Load, Save As, the Load and Quit questions, "Saved correctly"), with a modal game notice (`_PictureDialog`, game over), with About or Status, with the game's "Select a Game" and the opening's. The menu bar stays inert in these cases (`BarraMenus::so_sistema`: only the system menu opens and can be navigated). In the original, the opening does not respond to the buttons (test bench `qemu_selecao_moldura.txt`) and a modal dialog disables the main window (`DialogBox` calls `EnableWindow(FALSE)` on the owner) [hypothesis for SimAnt: Windows 3.1 behavior, not checked on the test bench]; so in Windows 3.1 you cannot even minimize with the dialog open — the port chooses to allow it.
- **Closing with a modal open:** Close from the system menu, double-clicking the box, Alt+F4 and closing by the system **always** open the Quit question (`Sessao::pedir_para_fechar`). An open dialog is canceled and the question opens in its place (in the original, Alt+F4 would go to the dialog, which treats it as Cancel — `DefDlgProc`: `WM_CLOSE` → `IDCANCEL` [hypothesis, same]); hold menus, Examine, mini map, mod menu, About and Status close first. With the Quit question itself (or the Save As from its Yes) open, nothing happens (beep). In the opening's "Select a Game", Close exits the program, like closing the window there. Before, Alt+F4 with a port dialog open exited without asking.
- **Alt+F4 exclusive to the executable (user request):** in the help window (WinHelp), closing moves from Alt+F4 (the original's) to **Ctrl+F4**; the help's system menu shows "Close Ctrl+F4" (`data/ajuda.json` → `janela.itens`). Alt+F4 always closes SimAnt with the Quit question. Divergence recorded in `docs/divergencias.md`.
- **When restored, the frame sits flush with the edges:** with the window resized to a size that is not a multiple of the game (or snapped by Aero Snap, or `--janela`), the thick frame was drawn around the centered game, with the black bars **outside** it, and the window looked frameless (user report). Now the frame is the window border (drawn at the game's scale, flush with all four edges, resizing through them) and the game is centered inside it, with the bars between the two (`moldura_janela.rs`).
- **Fixes along with it:** with a modal window on top (`Sessao::com_janela_modal`) the cursor is the arrow — the Experimental mode's ANT INFO magnifier (a cursor drawn by the port, with the system one hidden) stayed frozen over the Quit question and the mouse seemed stuck; releasing the button with a modal open ends a tool's drag. Keyboard accelerators (Ctrl+S, Ctrl+L, Ctrl+A, Ctrl+E, Ctrl+I…) redraw the frame immediately (the dialog only appeared on the next event, because the simulation stops while it is open and nothing else requested the redraw).
- **Discarded:** leaving the buttons inert with a modal, like Windows 3.1 (the user asked for them to work; the bar is the executable's frame); ignoring Close with a dialog open (Alt+F4 would look broken); keeping Alt+F4 in the help (two meanings for the same key).
- **Impact on mods:** none on the API (same formats). A mod that brings its own `video.json` without `moldura_windows31` now gets the frame on; `data/ajuda.json` changes only the shortcut text.

## 2026-10-19: Speed pacing: Fast ≈ 2.5× and Ultra ≈ 5× Normal (user decision)

- **Decision (user's, after playing):** "fast and ultra are much too fast; make fast about 2.5× normal and ultra 5× normal". `data/partida.json` → `relogio.ritmo_velocidades` with `modo` `"proporcional"` (default) or `"original"`, `ticks_por_segundo_normal` (6.0606: the original's Normal, 1 tick every 3 messages of 55 ms) and `multiplicadores` per `_GameSpeed` (`[null, null, 2.5, 5.0]`; `null` = the original's rule, Slow and Normal stay as they are). In proportional mode, Fast runs at 15.15 ticks/s and Ultra at 30.3 (in the original, measured: ~55–66 and ~91). Implementation (`Partida::mensagem_de_timer`): the iterations of the `MYTIMERFUNC` loop per message come from a credit (multiplier × normal × 55 ms per message, with the fraction kept and a cap against bursts after a pause), as on a slower processor; in Fast/Ultra each iteration runs one tick, so `_gameCycles` stays equal to the ticks. The tick, `_GameSpeed`, the save and the per-speed redraw (`redesenho_mapa_a_cada`) do not change; the tick vectors are the same (test `os_ticks_sao_os_mesmos_em_qualquer_ritmo`). The test bench 486's pacing is available via `"modo": "original"`, `--velocidades original` or the launcher's "Fast/Ultra do 486" checkbox.
- **Reason:** in the original the Fast/Ultra pacing depends on the CPU (the busy loop); the test bench's 486 is too fast to play. Normal and Slow come from the Windows clock and stay faithful.
- **Discarded:** shortening the message interval (would change Slow and Normal and `_TickCount`); skipping iterations without a tick (`_gameCycles` would advance more than the ticks in Fast, which the original never does); changing `voltas_por_periodo` (integers: cannot give 2.5×).
- **Impact on mods:** API 0.38, new optional key (missing = the original).

## 2026-10-19: Slow when unfocused (user decision)

- **Decision (user's):** "when the window loses focus, regardless of the pacing, automatically switch to slow speed, and resume the selected speed when focus returns". `data/partida.json` → `relogio.sem_foco_velocidade` = 0 (default; `null` = the original). Without system focus (another window active, or minimized), the cadence is Slow's (or the chosen one, if slower); with focus, it returns to the chosen one. Only the cadence (`Partida::velocidade_efetiva`, used in the iterations and in the loop delay): `_GameSpeed` does not change, so neither does the saved `.ANT`, the check mark in the Speed menu, nor the per-speed drawing. Command line `--sem-foco lenta|original`; "Lenta sem foco" checkbox in the launcher.
- **Reason:** the original keeps the pacing when unfocused (measured on the test bench, `qemu_ui_moldura_principal.txt`); the user prefers the colony not to run while they are in another window. Changing only the cadence prevents a save made while unfocused from recording Slow.
- **Discarded:** pausing when unfocused (the user asked for slow); switching `_GameSpeed` and switching back later (would affect the save and the menu).

## 2026-10-19: Simple synthesizer as the default (user decision)

- **Decision (user's):** "the simple one is the closest to the original; make it the default". `data/som.json` → `sintetizador` = `"simples"`; in the launcher, "Padrão" is the simple one and it comes first in the list. FM (`"fm"`) and SoundFont remain selectable (`--sintetizador`, launcher).
- **Reason:** the user's perception prevails for the default. The 2026-10-19 measurement ("FM path") said the opposite (FM's chroma, spectrum and treble closer to the DOSBox-X capture); it remains recorded there, and FM stays as an option for those who want the Sound Blaster timbre.
- **Impact on mods:** a `som.json` mod that relied on FM by default must specify `"sintetizador": "fm"` (API 0.38).

## 2026-10-19: Windows 3.1 frame in place of the system one (user decision)

- **Decision (user's):** "make the Windows 3.1 frame replace the game window's frame, to better simulate the Windows 3.x aesthetics". With `moldura_windows31` on and `data/video.json` → `substituir_moldura_do_sistema` (default `true`), the SDL window is created borderless (`SDL_WINDOW_BORDERLESS`, with the hints `SDL_BORDERLESS_RESIZABLE_STYLE`/`SDL_BORDERLESS_WINDOWED_STYLE`, which give Windows the titled, resizable window style without drawing it) and `SDL_SetWindowHitTest` (`simant/src/moldura_janela.rs`) says: the title strip drags (`HITTEST_DRAGGABLE`: Windows moves the window, maximizes/restores on double-click, snaps to the top of the screen and on Win+↑), the thick frame resizes (sides, and corners up to the marks, as in Windows 3.1), the rest (system menu box, buttons, game) belongs to the game. The drawn buttons act on the system window: minimize minimizes; the right one is **maximize** (up arrow) with the window restored and restore with it maximized; the system menu switches Restore/Maximize according to the state (Move and Size are grayed out: moving and resizing are done with the mouse); Close, double-clicking the box and Alt+F4 ask the Quit question. When restored, the window gets the 4-pixel thick frame of Windows 3.1 (`data/moldura_principal.json` → `borda`: black lines, light gray in the middle, corner marks at 4 + 18); maximized, no frame, like the original. Scaling moved from SDL's logical screen to `moldura_janela.rs`, because the borderless maximized window extends beyond the monitor's work area by the invisible frame (9 pixels at 125%): the game is scaled by integers (or not, `escala_inteira`) inside the visible part, with bars. `--moldura-do-sistema` (or `"substituir_moldura_do_sistema": false`) goes back to the bar inside the system window.
- **Evaluation of leaving the frame on by default:** with the frame chosen in the launcher ("Moldura Win 3.1" checkbox), the replacement is already the default. `moldura_windows31` stays `false` in `data/video.json`: the test exports and captures (`--exportar-telas`, comparisons with the test bench) are of the client area without the bars, and turning the frame on by default would change those results and the window of anyone running from the command line. It is up to the user to decide whether they want it on by default.
- **Verified on Windows 11 (125%), without using the user's mouse or keyboard:** messages to the window (`WM_NCHITTEST` on the strip = `HTCAPTION`, on the edges and corners = `HTLEFT`/`HTTOP`/`HTTOPLEFT`/`HTBOTTOMRIGHT`, on the buttons = `HTCLIENT`; `WM_NCLBUTTONDBLCLK` on the strip maximizes and restores; `SC_MINIMIZE`; Alt+F4 opens "SimAnt Quit") and captures of the restored window (648 × 488 with the frame) and maximized (scale 2, inside the work area). Not verified: dragging and resizing with a real mouse and clicks on the drawn buttons (posted mouse messages do not reach SDL); Linux (SDL's hit test works on X11 and Wayland, but was not tested).
- **Discarded:** dragging the window through the game itself (`SDL_SetWindowPosition` on every movement: jittery, no system snapping); letting SDL scale with the logical screen (the maximized game would lose its edges under the invisible frame).
- **Impact on mods:** API 0.38: `moldura_principal.json` → `borda` (optional) and `video.json` → `substituir_moldura_do_sistema`.

## 2026-10-19: Launcher inside `simant`, drawn in SDL2 (no egui), with native dialogs

- **Decision:** the startup options screen ("launcher") is part of `simant` itself (`simant/src/launcher/`), drawn in software on top of the SDL2 the port already uses, in the style of Windows 3.1 dialogs, with an embedded public-domain 8 × 8 font (`font8x8` by Daniel Hepper, derived from IBM's public-domain VGA fonts). The folder and file pickers are the system ones: on Windows the common dialog (`IFileOpenDialog` via COM, called directly, no new crate); on Linux `zenity` or `kdialog`, if installed (without them, you type the path, or drag the folder onto the window). The choices are stored in `launcher.json` in the user data folder (`config_launcher.rs`), which is just a stored form of `--` options: the screen shows the equivalent command line, editable, and `simant` puts these options before the command-line ones, which win. Flow: `simant` opened **without options** (double-click) shows the launcher; "Jogar" closes the launcher and starts the game in the same process. With "Abrir esta tela ao iniciar" unchecked, double-clicking goes straight to the game (the launcher comes back with `--launcher`, or by itself if the game folder stops being valid). With options on the command line, the configuration goes underneath: all of it except startup; only the game folder in test runs (`--ticks`, exports...), so as not to change the comparisons; `--sem-config` ignores it.
- **Reason:** a single executable in the package (the simplest for whoever downloads the `.zip`: one `simant.exe`, no choosing between two); no new dependency, no new license beyond the font's public domain; Linux CI needs nothing beyond the `libsdl2-dev` it already installs; the release executable grew 0.27 MB (6,053,376 bytes against 5,784,576, measured on Windows); the screen works without any game file (it is where you choose the folder) and can be saved to a PNG without opening a window (`--capturar-launcher`), which produced the capture `docs/imagens/launcher.png` and a test that runs in CI.
- **Discarded:** (a) separate binary `simant-launcher` with **egui/eframe + rfd**. Pros: ready-made widgets (text fields with selection, scrolling, accessibility), modern look. Cons: on the order of 150 more crates and a few more MB in the package [estimate, not measured: nothing was compiled with egui]; licenses beyond MIT/Apache (egui's default fonts are OFL-1.1 and Ubuntu Font License, and there is Unicode-3.0), all permissive but to be recorded; `rfd` on Linux requires GTK3 (`libgtk-3-dev` in CI and GTK on the player's system) or the asynchronous XDG portal stack (zbus and co.); two executables in the package and the question "which one do I open?"; much longer compile time. (b) Old folder dialog `SHBrowseForFolder` (simpler, but the folder tree is worse to use than the modern dialog). (c) Choosing the folder inside the game window with the original's fonts (impossible before finding the folder). (d) Only documenting `--jogo`/`SIMANT_DIR` (requires a terminal or an environment variable, hard for players).
- **Game folder priority:** `--jogo` > `launcher.json` > `SIMANT_DIR` > `SimAnt-T/MAXIS/ANTWIN` in the port folder. The variable sits below the configuration because it is the old way (from the earlier READMEs) and the choice in the launcher is the most recent and visible.
- **New options:** `--launcher`, `--config ARQ`, `--sem-config`, `--capturar-launcher ARQ.png`, `--launcher-jogar-apos-ms N` (test), `--perfil-driver NOME` (the `perfil_driver` of `data/resolucao.json`, applied on top of the mods with `Recursos::sobrepor_dados`), `--desligar-mods A,B` (`Recursos::abrir_sem`), `--com-som`.
- **Impact on mods:** none on the API (same format and functions). The player can disable mods without removing them from the folder; an enabled mod that depends on a disabled one gives an error like a missing dependency (`docs/api-mods.md`, "Loading and life cycle").

## 2026-10-19: Executable without a console on Windows; log and error box

- **Decision:** the **release**-profile `simant.exe` is a windowed program (`#![windows_subsystem = "windows"]`, with `cfg_attr` only outside `debug_assertions` and `test`): double-clicking does not open a console. The debug one (`cargo run`) stays a console program. Without a console and without redirection, the output (mods' `[script]`, warnings, errors, panics) goes to `simant.log` in the user data folder (the previous one is kept in `simant-anterior.log`), and fatal errors also appear in a message box (`SDL_ShowSimpleMessageBox`), with the log path. With the output redirected by the caller (tests, scripts, `simant.exe > saida.txt`, CI) nothing changes. `--console` attaches the console of the calling terminal (`AttachConsole`) or a new one (`AllocConsole`); the Windows package includes `simant-console.bat` (which calls `simant.exe --console` and waits for a key at the end). On Linux, the same log applies only when the program is opened without options and without a terminal (file manager); with options, the output stays where the caller put it. Implementation: `simant/src/registro.rs` swaps the process's standard output handles (`SetStdHandle`/`dup2`), so the `println!`/`eprintln!` of the port and the engine do not change.
- **Reason:** requested for 1.0: the console opened alongside the game was confusing, and an error (wrong game folder) closed the console before it could be read.
- **Discarded:** `windows_subsystem` in the debug profile too (`cargo run` would lose the output in the terminal); a separate console binary (two nearly identical executables in the package); replacing all `println!` with a logging library (many changes, including in the engine, for the same result); automatic `AttachConsole` whenever there is a parent terminal (`cmd` does not wait for windowed programs and the output gets mixed with the prompt).

## 2026-10-19: Port folders relative to the executable

- **Decision:** `data/`, `mods/` and the default `SimAnt-T/MAXIS/ANTWIN` are in the port's **base folder**: the executable's folder if it has `data/`, otherwise the current folder, otherwise up to three folders above the executable (the repository's `target/<perfil>/`) (`simant/src/pastas.rs`). Relative paths given in `--jogo`, `--dados` and `--mods` are resolved from the current folder and, if they do not exist there, from the base (`--mods exemplos/mods` works from any folder).
- **Reason:** the package needs to work from anywhere and by double-click (shortcuts, "Open with", a terminal in another folder). Before, everything was relative to the current folder and Linux needed `simant.sh`.
- **Discarded:** only the executable's folder (would break `cargo run` at the repository root); an environment variable for the base folder (one more step for players).
## 2026-10-19: Original's texts read from the user's installation, not stored in `data/`

- **Decision (user's):** the SimAnt texts that were copied into `data/*.json` (ribbon phrases, file boxes and dialogs, window titles, tutorial name and title, pause item, main window and help titles) and the bitmap pieces of the boy's speech balloon are now read from the user's installation at run time. The JSON files store only the **reference** to the source (type 4 string list in the database, window layout object, `SIMANTW.EXE` segment, `.HLP` title), resolved by `Recursos::dados` (`engine/src/recursos.rs`). Inventory and analysis in `docs/lancamento.md` §6.
- **Reason:** the port is distributed under "MIT OR Apache-2.0" and must not carry Maxis text; most texts already came from the user's database (`SHARED`), and these were the exceptions. Reading from the source also makes explicit where each text comes from.
- **Discarded:** (a) keeping the texts in `data/` (redistributes Maxis phrases); (c) only stating in the license that these excerpts are not covered (the text would remain in the package). Numeric tables extracted from the executable stay (facts and rule parameters, in our own format; §6.3 of `lancamento.md`).
- **Impact on mods:** API 0.35. A mod that brought the text keeps working (a string replaces the reference through key merging); external tools that read `data/*.json` find objects in place of those strings.

## 2026-10-19: Windows 3.1 title bar optional (`moldura_windows31`), off by default

- **Decision:** the port draws the Windows 3.1 main window title bar and system menu (measured on the test bench, 100% against the captures; `telas/menus.md` §8) only with `data/video.json` → `moldura_windows31` = `true` (or `--moldura`). The default is `false`. With it: Minimize minimizes the system window, Close (and double-clicking the box) asks the Quit question like the original's `SC_CLOSE`, Restore restores the system window only if it is maximized, Switch To… does nothing; the title becomes inactive without focus, with a Windows dialog open or with the help viewer focused.
- **Reason:** the original runs maximized and the bar is part of its screen, but in the port the current system window already has a title, minimize and close: two title bars in a row take up 19 lines and confuse players. For those who want the original's whole screen (comparing with captures, fullscreen, large scale), the option gives exactly 640 × 480 and the arrow-key path through the box (← on File, → on Speed).
- **Discarded:** always drawing it (redundant with the system frame); a window without the system frame with only the Win 3.1 bar (loses dragging and resizing by the current system); Switch To opening something else (there is no equivalent Task List that makes sense).
- **Impact on mods:** API 0.33: `moldura_windows31` in `video.json` and the new file `moldura_principal.json`, both optional and merged by key.

## 2026-10-19: Unfocused, the simulation pacing is the same

- **Decision:** `data/partida.json` → `intervalo_sem_foco_ms` = 17 (it was 170, the value in the code, which the port rounded to 220 ms per message).
- **Reason:** measured on the test bench: 61 ticks in 10 s with the window active, with the Windows Task List in front, and minimized (`regras/simulacao-visao-geral.md` §1). The original is the oracle; the mechanism that cancels the code's 170 ms was not found.
- **Discarded:** keeping the pseudocode's 170 ms (the port ran ~4 times slower when unfocused).

## 2026-10-19: FM path: own OPL synthesizer and own GM bank, default for the music

- **Decision:** the port gets a third synthesizer, `"fm"` (`simant/src/som/fm.rs`), chosen by `data/som.json` → `sintetizador` (or `--sintetizador`), and it becomes the default. It is our own Rust implementation of an OPL2/OPL3-style synthesizer (2 operators, the chip's fields and timing tables, 8 waveforms, feedback, LFO; not cycle-accurate), with its own MIDI driver (18 voices) and its own GM bank (`data/opl_banco.json`, generated by `tools/gerar_banco_opl.py`, project license). A user's `.op2` bank can be read at run time (`fm.banco_op2`), without going into the repository. The bank's `ganho` was calibrated so the music sits, relative to the effects, where the original's capture showed (−20 dB from an effect with gain 1). `--exportar-som` now records the music with `volume_musica`.
- **Reason:** the capture of the original in DOSBox-X (SB16 + OPL3, MIDI Mapper "SB16 Ext Synth" from the user's installation; `regras/som.md`) gave the first timbre reference. In the opening, FM is closer to the original than the simple synthesizer in every measure (aligned chroma 0.849 against 0.819; mean spectrum correlation 0.677 against 0.590; energy above 4 kHz 5 % against 18 %, the original has 6 %; without the white-noise percussion, which the original does not have), with no extra file and no third-party license.
- **Discarded:** existing OPL emulators in C (Nuked-OPL3 is LGPL, which complicates static linking; DOSBox/MAME because of the license and for being third-party code); Rust OPL crates (none checked with adequate license and maintenance without a new dependency tree); known GM→OPL banks (Creative's, embedded in the driver, and those of DMX/Apogee/Miles games are proprietary; others have uncertain licenses) — the `.op2` format is accepted only as a user file; extracting the bank from the user's `VSBPD.386`/`SB16FM.DRV` (would require reverse engineering the driver; it could be a future run-time reading path).
- **Impact on mods:** API 0.31: keys `sintetizador` and `fm` in `som.json` and the new file `opl_banco.json`, both overridable by key; a `som.json` mod that depended on the simple synthesizer or on the SoundFont must specify `sintetizador`.

## 2026-10-19: Color and position reference: standard Windows 3.1 VGA (driver profile)

- **Decision:** by default the port imitates Windows 3.1 with the **standard VGA** driver (`VGA.DRV`, 16 colors): the driver's system colors (active title and dialog frame dark blue, application background white) and 8-pixel byte alignment of windows and dialogs. The opening and the game now use the same reference. What depends on the driver lives in `data/resolucao.json` → `perfis_driver` (`"vga"`, `"svga256"` for vbesvga/S3 in 256 colors, `"s3_dosbox"` for the screens validated on DOSBox-X), chosen by `perfil_driver`. See `docs/spec/telas/resolucao.md` §7.
- **Reason:** the opening came from the DOSBox-X captures (S3, 256 colors: light blue and cream) and the game from the QEMU bench (VGA, 16 colors: dark blue and white). The difference is not the game's: `WIN.INI` has no `[colors]`, and each driver brings its own default colors (resource `OEMBIN 1`); the 1-to-4-pixel differences in x come from the `CS_BYTEALIGNCLIENT` of the game windows' class, which only acts in planar video. Standard VGA is what every Windows 3.1 has and is the environment of the automated test bench (where most of the game references are).
- **Discarded:** keeping the two references mixed (the screen changes colors between the opening and the game); using DOSBox-X's S3 as the default (would require redoing the game measurements, and S3 has one extra pixel with no explanation in Windows); emulating the test bench's 6-bit DAC (the driver's logical colors are the same; the DAC belongs to the emulator).
- **Consequences:** the hashes of the screens validated against DOSBox-X do not change (the tests use the `"s3_dosbox"` profile); the title at 640×480 matches the VGA test bench 99.96% (before, 84.88%). Mods: API 0.29 (`docs/api-mods.md`).

## 2026-10-19: Virtual screen (`resolucao_virtual` in `data/video.json`)

- **Decision:** the port imitates a Windows 3.1 screen of 640×480 (default), 800×600 or 1024×768. The resolution chooses, by the original's rule stored in `data/resolucao.json` (client area = screen − 38 lines; position table 9/0 up to 480 lines, 9/8 above), the client area size and the position table of the opening and the game. Scaling remains that of the "Scale 1" decision (integer, sharp), applied over the virtual screen. Command line: `--resolucao LxA`. Specification: `docs/spec/telas/resolucao.md`.
- **Reason:** coordinator's request; the original changes layout with the resolution (the control windows move below the edit window on larger screens), and the port mixed the two: the opening at 800×562 (DOSBox-X) and the game at 640×442 (test bench).
- **Consequences:** the default opening becomes 640×442 with table 9/0 (as on the test bench); `jogo.json` → `tabela_posicoes` and `tela_jogo.json` → `largura`/`altura`/`tabela_posicoes` no longer apply in the executable (API 0.27) and remain for the tests and examples, which do not change.
- **Discarded:** scaling the game to fill a larger screen (the original does not; it would be fractional scaling); accepting any resolution (only the three have known behavior and the original's rule has only two tables); tables and sizes per resolution written by hand in each data file (the original's rule is a single one and fits in one file).

## 2026-10-19: Mod API 0.26: key merging, hooks inside the tick, script state next to the save

- **Decision:** (1) the mods' `data/*.json` are merged by key over the port's: objects merge, lists and values replace, `"_substituir": true` in an object replaces the whole object; (2) `antes_<parte>`/`depois_<parte>` hooks around the 13 subroutines of the tick, through a wrapper of the rules (`scripts::RegrasComScripts`) used only when some mod defines one of them; (3) the scripts' state goes to `NOME.ANT.mods.json`, next to the `.ANT`, with the save's `_GameTime` to recognize a side file from another save.
- **Reason:** `CLAUDE.md` asks for "mods override data by key"; replacing the whole file forced each mod to keep up with the new keys of each version. Lists do not merge item by item because almost all of them are positional tables from the executable (half a table from another version would be a silent error). The wrapper leaves `rules::tick::tick` intact and costless without mods (the tick vectors must not change). The side file keeps the `.ANT` readable by the original, which is the oracle.
- **Discarded:** JSON Merge Patch (RFC 7386), in which `null` deletes the key: several files use `null` as a value (`video.json`, `som.json`); merging lists by index; calling the part hooks from inside `tick` with an `Option<&mut Scripts>` (would change the signature used by the tests and the tools); storing the mods' state inside the `.ANT` (the original has no field for it, and an extra block would break its reading); executing the actions requested in the part hooks immediately (they need the whole `Partida`, which is borrowed by the tick: they run right after it).
- **Impact on mods:** compatible for those who bring the whole file, except for keys omitted on purpose (see the 0.26 history in `api-mods.md`).

## 2026-10-18: Common rule tables in `data/comum.json`; `jogo.json` overridable

- **Decision:** the 14 tables that the original has only once and that several parts of the rules use (`_Dx8`/`_Dy8`, `_Dx9`/`_Dy9`, `_TurnTab`, `_UnCarryCaste`, `_ModeTabWB`/`_ModeTabSB`/`_CasteModeTabB`, `_SowTab`, fight class and matrix, hole and antlion edge) leave the `data/<parte>.json` files and go into `data/comum.json`, with the address of each one (`_enderecos`) and the parts that use it (`_usado_por`). Each part completes its JSON with them when loading (`rules/comum.rs`, `completar_com_comuns`); the parts' structs did not change. `tools/extrair_comum.py` generates the file; the other extractors no longer write the copies, and `tools/conferir_extracoes.py` checks that all of them reproduce the `data/*.json`. Mod API 0.20.
- **Compatibility:** an old mod that brings the copy in a part's file keeps working **only for that part**, with a console warning. Reason: that was the behavior the mod had (the author may have deliberately changed only one part); ignoring the key would change the game of whoever uses the mod with no visible warning in the game.
- **`jogo.json`:** is now read by the `Recursos` with mods, before opening the databases (a `Recursos` without databases is opened just to read the file). A mod can, for example, swap `WINGANT` for `MWINNT` (monochrome bitmaps) or the window position table.
- **Reason:** a mod that changed one copy and forgot the others left the game inconsistent (for example, a different `classe_luta` on the surface and in the nest), which the original does not allow; and `CLAUDE.md` asks for overridable data.
- **Discarded:** ignoring the old key with a warning (silently breaks existing mods in the game); partial key override in all files (bigger; it is in "Planned" of `api-mods.md`); an "aliases" table for `boca_aranha_x/y` of `inimigos.json` (it is another table of the original, `_SeatX`/`_SeatY` at `8:87ec`, which merely has the same values as `_Dx8`; it stays in `inimigos.json`).

Ribbon 35 buttons (`yarduserbuttonN`): the port does not have these configurable buttons yet; when it does, they go into the same file. (Update: they went in on 2026-10-18, `botoes_quintal`.)

It looks for `WINDOWS/WIN.INI` in the game folder and in the two above it (the typical installation is `C:\MAXIS\ANTWIN` + `C:\WINDOWS`; the user's, `SimAnt-T/MAXIS/ANTWIN` + `SimAnt-T/WINDOWS`), or the file given by `--win-ini`. Reason: whoever has already played the original starts with their options and buttons. The file belongs to the user and is not versioned. The path is not in `data/` because it is not game or mod data, it is the shape of the installation; the command line covers other installations. Discarded: always reading `WIN.INI` (the port's file would have no effect after changing an option in the port); copying `WIN.INI` into the repository (it belongs to the user).

## 2026-10-18: Scale 1 by default and video options in `data/video.json`

- **Decision (user's):** the window opens at **640×480 at scale 1**, like the original (the game area, 640×442, plus the system frame). Scale and size are configurable in `data/video.json` (`escala`: integer, 0 = the largest that fits; `janela`: initial `[largura, altura]` or `null`; `redimensionavel`; `escala_inteira`) and on the command line (`--escala N`, `--janela LxA`), which wins over the file. The system window can be resized and maximized: with `escala_inteira` the game scales only by integer multiples, centered with bars (SDL's `set_integer_scale`); without it, it fills the largest rectangle with the game's aspect ratio. It is never smaller than the game's resolution (`set_minimum_size`). The sharpness of the decision below (DPI + nearest neighbor) remains.
- **Reason:** the user found the automatic scale (the largest that fits, 2 on their monitor) "too big" and asked for the original's, with scale and size configurable in the future.
- **Where it lives:** `data/video.json`, read by the `Recursos` (a mod can replace it; the file is optional: without it, the defaults above). Code: `simant/src/video.rs` (with tests for the initial size calculation and the precedence).
- **Discarded:** a port `simant.cfg` (would be confused with the original's `SIMANT.CFG`, of a different format); a preferences file outside `data/` (one more place to look; may come later, if there are more player preferences).

## 2026-10-18: Sharp window: DPI-aware, integer scale with nearest neighbor

- **Decision:** before `SDL_Init`, `SDL_WINDOWS_DPI_AWARENESS = permonitorv2` and `SDL_RENDER_SCALE_QUALITY = 0`; the window keeps a logical resolution (`set_logical_size`) and integer scale (`set_integer_scale`), with bars when the size is not a multiple.
- **Reason:** the user found the game "kind of blurry". On their machine the screen has 125% scaling (1920×1080 physical, 1536×864 logical): without DPI awareness the 640×442 window came out at scale 1 and Windows enlarged it 125% with a bilinear filter. DPI-aware, the screen limits come in physical pixels and the scale becomes 2 (1280×884), all done by the renderer. **Checked:** the window capture (`--capturar-janela`) has 0 non-uniform 2×2 blocks, only the 16 palette colors, and the ribbon is identical, pixel by pixel, to the exported frame (`--exportar-tela-jogo`) enlarged 2×.
- **Discarded:** fractional scaling to fill the screen (blurs or distorts the pixels); `SDL_WINDOW_ALLOW_HIGHDPI` (on Windows, SDL 2.30 keeps giving logical window coordinates, and the scale calculation would live in two systems).

## 2026-10-18: Windows fonts for titles and dialogs: those from the user's installation

- **Decision:** the window titles and the Windows dialogs (message box, file dialog) use the fonts of the Windows 3.1 itself that comes with the user's game: `WINDOWS/SYSTEM/VGASYS.FON` (System) and `WINDOWS/SYSTEM/SSERIFE.FON` (MS Sans Serif 8, in simulated bold as GDI does), read at run time through the font list of `data/interface.json` (indices 6 and 7). Nothing from them is versioned. Without the files, it falls back to the game's font 0 (`Gaia8x14`).
- **Reason:** the request was to imitate the system font; the fonts are in the installation the user already provides (like `FONTRES.FON`), the `.FON` parser already existed, and the result matches the captures 100% in the titles.

## 2026-10-17: Lua mod scripts: one VM per mod, hooks outside the tick, limits and errors that disable the mod

- **Decision:** `mlua` 0.11 with Lua 5.4 compiled from source (features `lua54` and `vendored`: does not depend on an installed Lua, compiles with MSVC on Windows and with gcc on the Ubuntu CI). Each mod with `"scripts"` has its own Lua machine, created with `Lua::new_with` with only `table`, `string`, `math` and `utf8`; from the base library, `load`, `loadfile`, `dofile`, `require`, `collectgarbage`, `print` (becomes `registrar`) and `warn` are removed, and from `string`, `dump` is removed; chunks in text mode only. The game appears as an `estado` object (scoped userdata, `Lua::scope`) valid only during the call, with reads that return copies and four validated writes. The hooks (`ao_iniciar`, `antes_do_tick`, `depois_do_tick`, `ao_evento`) run in `core::partida`, before and after `rules::tick::tick`, and only if some active mod defines them. The script's randomness is a per-mod xorshift32 (seed = FNV-1a of the name), also exposed as `math.random`.
- **Limits:** per call, 1,000,000 instructions (checked every 1000 by the instruction hook) and 250 ms; per mod, 16 MiB of memory (`set_memory_limit`). `pcall`/`xpcall` are wrapped to pass the limit error on. Any error disables only that mod's scripts, goes to the log and generates a warning on the ribbon.
- **Reason:** faithfulness to the original cannot depend on mods: without a script, nothing changes in the loop, and with a script the S and R random draws remain the game's alone (the tick vectors stay the same). One VM per mod isolates errors and limits, and the scoped object prevents the script from keeping a reference to the state. Counted instructions are deterministic; time is only extra protection (a slow C function, like a huge `string.rep`, is not interrupted midway; memory limits it).
- **Discarded:** hooks inside the tick, per rules part (would change the order of `_DoAntSim` and require their own vectors; left for later); a single VM for all mods (one error or memory overflow would bring them all down); Lua's `math.random` (random seed, not reproducible); a command queue applied after the hook (the script would not see the effect of its own write); Luau (ready-made sandbox, but it is another language and the user's decision was Lua).
- **Impact on mods:** API 0.12, additions only (docs/api-mods.md, "Lua scripts").

## 2026-10-17: Audio: SDL2 + MIDI synthesizer in Rust (`rustysynth` with SoundFont, or simple synthesizer)

- **Decision:** the executable plays audio through a single SDL2 device (`AudioCallback`, stereo `f32`), with its own mixer (`simant/src/som/mixer.rs`) that sums one music track and one effect. Type 5 effects are decoded by `engine::formats::som` and resampled from 4096 Hz to the device rate. The music (`SOUND\*.MID`) is read by `engine::formats::midi` and played by our own sequencer that delivers the channel messages to a synthesizer: **`rustysynth`** (pure Rust, MIT license) when there is a `.sf2` SoundFont (`--soundfont`, `SIMANT_SOUNDFONT` or `soundfont` in `data/som.json`), otherwise a **simple synthesizer of our own** (basic waveforms per General MIDI family, noise and decaying sine for the percussion).
- **Reason:** the original plays MIDI through Windows MCI, that is, through whatever synthesizer the machine has; there is no "right" timbre to reproduce. A GM SoundFont gives the result closest to a period sound card, but it cannot be distributed with the port (size and license vary), so it is configurable. The simple synthesizer ensures the game has music without any extra file. Pure Rust avoids native dependencies beyond SDL2. The same mixer serves the export to WAV (`--exportar-som`), which allows testing without playing sound.
- **Discarded:** `SDL_mixer` with Timidity (one more native library and patch configuration); FluidSynth (large C library); the operating system's MIDI (`midiOut` on Windows: not portable, no export to WAV); converting Windows' `gm.dls` (DLS format, no pure-Rust reader and uncertain license).
- **Impact on mods:** `data/som.json` (id → file table, volumes, rate, channels, music source) is overridable; music can be replaced in `arquivos/sound/<nome>.mid` and effects in `objetos/5/<id>.bin`.

## 2026-10-17: Common rules module (`rules/comum.rs`) and tables in `RegrasOriginais`

- **Decision:** the routines that the original has only once and that several parts call live in a single place, `engine/src/rules/comum.rs`: type and tile tests (`grupo`, color, soil, food, solid, yellow), `_GetDir`, `_GetDis`, `_Bounce`, per-plane access (`_GetMap`, `_GetLife`, `_IsClearTile`, `_IsNotObstacle`, `_IsThisPebble`, `_IsItHole`, `_TileCanBeMovedOn` on the surface, `_GetBestDir`), lists (`_FindInAList`, `_FindAntIndex`/`_FindInB/RList`), `_DeadAntHere`, `_PickupFoodA`, `_DropFoodA`, `_Recruit`, `_UnRecruit`, `_GetWinner`, `_GetNewMode`/`B`/`R`, `_KillSpider`, nest food (`_EatFood*`, `_StealFood*`), `_DecEat*`, `_PlaceEgg*`, `_ExitHole` and digging (`_DigTile*`, `_DigTileThem*`, `_SmoothEdges*`, `_FixExitMap*`, `_IsClear3x3`, `_MakeNewHole*`). The directions (`_Dx8/_Dy8`) and `_TurnTab` are read through the traits `Direcoes` and `TabelaDeGiro`, implemented by each part's table. Digging is written over the `Terreno` trait (with `Superficie`), implemented by `Estado` (tick) and by the world generation's `Mundo` together with its S generator, so that generation and the tick use the same code. The yellow ant's routines (`_YellowFight`, `_DoTroph`, `_YellowDeath`, `_MoveMyLife`, `_SetMyHealth`) are in `amarela.rs` and are called by the other parts.
- **Tables:** `RegrasOriginais` holds each part's tables (`quintal`, `inimigos`, `superficie`, `feromonios`, `ninho`, `amarela`, plus `geracao`) and the tutorial state outside the save (`memoria_tutor`, `interface_tutor`). `RegrasOriginais::carregar(&Recursos)` reads everything from `data/` with mods; `RegrasOriginais::default()` uses the embedded copies (tests). Each part's public functions receive the tables explicitly (those that kill or feed the yellow ant also receive `&TabelasAmarela`). The tick's smell phase (`_DoSmells`) became the method `RegrasSuperficie::fase_de_cheiro`, whose default runs with the embedded tables.
- **Reason:** each part was written by a different agent and had its own copy; the copies diverged in details (see below), the points that depended on the yellow ant were empty or provisional, and a mod that replaced `data/<parte>.json` did not reach the tick. A single routine guarantees that a fix applies to all parts, as in the original.
- **Divergences between the copies, and what was kept:** (1) `_GetNewMode` with a strategic mode outside 0..5: the nest used the table's last row, the surface returned mode 0; the last row was kept (invalid state; the original would read the following memory). (2) `_DropFoodA` in the house with tile 0x27–0x3F ("the food falls", a table the port does not have): the yellow ant returned success, the spider failure; success was kept (the original returns success after the fall; the spider does not use the result). (3) `_GetDis`: the surface truncated to 16 bits; `_GetDis` returns 32 bits (quintal.md) and only the surface truncates, in the caller. (4) The surface's `_YellowFight`/`_DoTroph` were partial (no `_YellowDeath`, no yellow ant turning toward whoever feeds it, no `_LessonTemp`); those from `amarela.rs` were kept. (5) The enemies' `_YellowDeath`/`_MoveMyLife` were provisional (no animations, messages or reincarnation); those from `amarela.rs` were kept. (6) The agony of `_KillSpider` was the constant 500 in the yard and `aranha_agonia` in the enemies; the data value was kept. (7) `TabelasSuperficie::carregar` read the file from the game folder (`Recursos::arquivo`) instead of `data/`; fixed. (8) The tutorial's `_SetMyHealth` had a hardcoded 100 and 9; it uses the one from `amarela.rs`. The other copies were equivalent (they differed only in unreachable boundary tests). No difference changes the original's tick vectors (identical score before and after, in all scenarios).
- **Two similar routines that stayed separate** (the original also has two): `_GetBestDir` (common) × `_GetRedBestDirs` (surface, uses `_TileCanBeMovedOn`) × `_GetMyBestDirs` (yellow ant, with the rules for rows 0–1 and for digging); `_MakeNewHole*` (common) × `_CreateNewHole` (yellow ant, the hole in its own cell); the yellow ant's `_EnterNest`/`_ExitNest` × the other ants' `_GoInNest`/`_ExitHole`.
- **Impact on mods:** no format changes. The rules' `data/*.json` now apply in the tick (mod API 0.5, see `api-mods.md`). The tables repeated across files (`dx8`, `turn_tab`, fighting, modes, hole edge) remain one copy per file, each applying to its own part; merging them into a `data/comum.json` would change the format and is left for when there is partial key override (done later, with the old copies accepted: see "Common rule tables in `data/comum.json`", API 0.20).
- **Discarded:** a `Mundo` converted to `Estado` before generation (generation needs its own generator and the raw vectors, and the `geracao_quick2` test compares byte by byte); a single `data/comum.json` now (would break mods that already bring these files); keeping the copies and only documenting them (the divergences above show the cost).

## 2026-10-16: Simulation = single `Estado` + fixed tick + `Regras` trait per subject

- **Decision:** all simulation state lives in a single `Estado` value (`engine/src/rules/estado.rs`), with the 307 blocks of the `.ANT` in typed groups by subject and the run-time-only fields (S and R generators, life maps, tick counters, event queue). The tick (`engine/src/rules/tick.rs`) is a function `tick(&mut Estado, &mut dyn Regras)` that follows the order and periodicities of `_DoAntSim` and does the small, already specified parts (counters, feeding, compaction, `_CountAnts`, `_HistUpdate`, mode summary). The large subroutines are methods of six traits (`RegrasQuintal`, `RegrasInimigos`, `RegrasSuperficie`, `RegrasNinho`, `RegrasAmarela`, `RegrasConselhos`), with empty default implementations, combined in `Regras`. `RegrasOriginais` implements the game, one trait per file in `rules/`.
- **Reason:** the order of the tick is part of the rule (random draws in the right order), so it lives in a single place and is tested. Separate traits allow each subject to be written in its own file, in parallel, without conflict, and a subject not yet written simply does nothing. Explicit state, without globals, keeps the tests deterministic and allows byte-by-byte round trips with the `.ANT`. The rules do not touch audio or windows: they request messages, music and dialogs through `Estado::eventos`.
- **Impact on mods:** the scripting API does not exist yet, but the architecture defines the points that will be exposed:
  - **reading and writing `Estado`** through the named groups (`colonia(cor)`, `lista(area)`, `feromonios`, `amarela`...), not through the original's addresses. The field names are part of the API and will get a compatibility note when they are exposed;
  - **hooks per tick subroutine**: a mod will be able to wrap or replace a `Regras` method (for example, its own `RegrasNinho`) while keeping the rest of the game. The order of the tick stays fixed and out of the mods' reach, to preserve determinism;
  - **events**: messages and sounds requested by the simulation go through `Estado::eventos`, and a mod will be able to observe or add events;
  - **data**: speeds and new-game initial values are in `data/simulacao.json`, already overridable by mods.
- **Discarded:** global variables mirroring the original's memory (hard to test and to expose to mods); a single `trait Regras` with all methods and a single `impl` (each agent or mod would have to edit the same block); dispatch through a table of function pointers built at run time (loses type checking with no gain now; it may be the shape of the mod API later).

## 2026-10-16: World generation tables in `data/geracao.json`; sine read from the database

- **Decision:** the tables that world generation reads from the executable (`_Dx8/_Dy8`, hole and antlion edges, `_SowTab`, pebble shapes) live in `data/geracao.json`, generated by `tools/extrair_geracao.py` from `SIMANTW.EXE`. The sine table, which in the original is a database object (type 9 no. 1000), is read from the database at run time, like the other objects. The random generators (`engine/src/rules/rng.rs`) are values with explicit state, passed as parameters, without global state.
- **Reason:** data outside the code (principle 4) and exact reproduction of the original: the test `engine/tests/geracao_quick2.rs` is only deterministic if every call to the generator is explicit.
- **Impact on mods:** a mod can replace the whole `geracao.json` (per-file override, like the other `data/*.json`) or object 9/1000. The tile values used by the rules (hole 0x50, food 0x48, soil 0x2E...) and the fixed quantities of generation (20/30/100/128 objects, 200 units of food) remain as named constants in the code, documented in `docs/spec/regras/tiles-valores.md` and `geracao-mundo.md`; moving them to data is left for when there is a rules mod API, because changing them without changing the rules that test them would break the simulation.
- **Discarded:** copying the tables into Rust constants (prevents mods); reading the executable at run time (would require the `.EXE` in addition to the databases and an NE parser in the engine).

## 2026-10-16: Port language: Rust + SDL2, mods in Lua

- **Decision (user's):** Rust (stable, MSVC toolchain), SDL2 for window, input and audio, and Lua for mod scripts (sandbox via `mlua`, to be adopted when the mod system starts).
- **Reason:** single, fast binary, native tests (`cargo test`), strong types for the parsers, and Lua is the best-known mod language and easy to isolate in a sandbox.
- **Discarded:** C#/.NET + MoonSharp (a reasonable alternative, but would require the .NET runtime), Python + pygame (the simplest, but with weaker performance and distribution).
- **Organization:** Cargo workspace. The `engine` crate gathers `core`, `formats` and `rules`, with no window dependency. The `simant` crate is the executable with `render`, `audio` and `input` over SDL2. The modules follow the architecture of `CLAUDE.md`.
- **SDL2 on Windows:** without cmake on the machine, the `sdl2` crate does not compile SDL from source (feature `bundled`). That is why we use the official precompiled libraries `SDL2-devel-<versão>-VC.zip` (libsdl-org, GitHub), extracted into `vendor/` (in `.gitignore`). `SDL2.dll` is copied next to the executable.

## 2026-10-16: Automated test bench: QEMU + QMP on SvarDOS

- **Decision (user's, after research):** automated tests against the original run on QEMU (headless), controlled through QMP (`send-key`, `input-send-event`, `screendump`, `pmemsave`), with SvarDOS (EDR-DOS kernel) as DOS. Details in `docs/bancada-qemu.md`.
- **Reason:** in official DOSBox-X, keys injected by the host do not reach Windows 3.x, `AUTOTYPE` only works in DOS, and the mouse is relative and requires capture. QMP injects keyboard and mouse into the emulated hardware, captures without focus and reads memory.
- **Discarded:** FreeDOS (kernel 2043 refuses Windows; 2046 386 gives "Invalid Opcode"; with 2046 8086 WfW returns to the prompt; in addition, FreeDOS's SHARE has a write bug), DOSBox-X forks with QMP (keyboard through the BIOS buffer), Bochs (slow), 86Box (no API), otvdm (not faithful). Full comparison in `reports/Automação de testes Win16 emulado.md`.
- **Consequence:** the test bench uses 640×480 (generic VGA). For pixel-by-pixel comparison at 800×600, the reference remains DOSBox-X.
